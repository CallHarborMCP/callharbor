# Professional autonomous engineering flow

- GitHub Issues are the only backlog and status; inspect managed issues directly using `gh` with milestone and label filters, then check each selected issue's ownership marker in its body. Never adopt unrelated community issues.
- OpenCode and Paperclip use separate clones/worktrees and preferably distinct GitHub identities. Work on one issue/branch/PR per writing agent. No third-party task coordinators, Python GitHub wrappers, issue leases, heartbeat services, or custom test-of-tests.
- Before work, inspect open PRs belonging to your own managed issues, reconcile status and finish unfinished work before starting another issue. Keep docs and source in sync.
- Renovate dependency PRs are ordinary maintenance PRs, not agent-owned Issues. Review their diffs and upstream release notes, run required tests, fix migration regressions, then merge through protected main. Never auto-merge untested dependencies or invent a parallel dependency-management framework.
- Choose a dependency-ready `status:idle` issue. Comment `CLAIM: <agent>, GitHub @<account>`, set label `status:in-progress` (remove idle), reread comments/status. If an earlier active claim from another developer exists, back out and select another issue. The first claimant works; the other leaves it alone. Don't overengineer simultaneous claims.
- Use `gh issue list`, `gh issue view`, `gh issue comment`, `gh issue edit`, `gh pr create/view/checks/merge` and `gh run view` directly. No helper scripts for these normal GitHub operations.
- Implement production code and behavioral tests together. Independently review important changes. Go through branch -> PR -> actual required green GitHub CI -> merge -> verify clean green main -> comment evidence -> close managed issue. No direct push main, no bypassing required checks.
- Blockers: explain reproducible failure in issue, set `status:blocked`, work on others. On your next cycle resume an issue you previously claimed if unfinished, after inspecting its open PR. Do not take over another agent's active task.
- New scope or defect: create a new GitHub issue with milestone v1.0.0, label agent:callharbor, marker `<!-- callharbor-managed:v1 -->` in its initial body, and meaningful acceptance tests; no shadow state file.
- Developer tools: `.mise.toml` is the only Go/Node version manifest; use `mise install` once per checkout and `mise exec -- <command>` for local work. If mise is absent, install the official CLI in user space and verify it; do not write a toolchain installer or change the global environment. GitHub Actions uses `jdx/mise-action`. Go modules and npm lockfiles continue to manage application dependencies.
- Keep repo context small and current: AGENTS entry, locked product/architecture/security/testing/DoD, this process, durable learnings. No verbose cycle diaries, no duplicate policy copies. No AI-generated scripts except when there is a real engineering need standard tools cannot meet.
- Release is controlled by owner OpenCode, after every required issue/evidence and full real test suite; Paperclip contributes PRs, not a parallel release. Finish with GHCR+GitHub release, release evidence, completion marker PR. Be honest about absence of a live Telnyx call.
